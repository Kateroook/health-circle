## 1. Цілі та охоплення

### Мета

Забезпечити автоматизоване API-тестування всіх реалізованих ендпоінтів застосунку на рівні:
- коректності бізнес-логіки (happy path)
- обробки некоректних вхідних даних (negative cases)
- авторизації та захисту ресурсів
- валідації полів відповідно до Swagger-специфікації

### Що покриваємо в 2–3 тижні

| Модуль | Ендпоінти | Статус фічі |
|---|---|---|
| Auth API | login, logout, refresh, profile, password-setup, change-password, forgot-password, reset-password, resend-code | ✅ Реалізовано |
| Users API | create, get, modify, delete, update status, avatar (upload/get/delete), reset-password, fcm-token | ✅ Реалізовано |
| Groups API | get all, get by ID, create, update, delete, leave, join, regenerate invite, block/unblock, get blocked | ✅ Реалізовано |
| Contacts API | find all, create, update, delete, set alias | ✅ Реалізовано |
| Health API | GET /api/health | ✅ Реалізовано |

## 2. Обмеження та поза охопленням

В рамках поточного плану **не автоматизуємо**:
- Push-сповіщення (FCM/APNs) — потребують окремого мобільного стенду
- SMS-сповіщення — зовнішній провайдер
- Real-time зміни статусів через WebSocket/SSE
- Інтеграцію з API повітряних тривог
- Геолокацію
- Перевірку UI/UX (навігація, аватар-пікер, онбординг) — поза API scope

Ці напрямки фіксуються як **future scope** для WebdriverIO E2E-тестів.

### 5.10 Наскрізні сценарії (Auth flow)

| ID | Назва | Опис |
|---|---|---|
| AUTH-E2E-001 | Повний registration flow | `createUser` → `resendCode` → `setupPassword` → `login` → `getProfile` → порівняти дані |
| AUTH-E2E-002 | Повний forgot-password flow | `login` → `forgotPassword` → отримати код з БД → `resetPassword` → `login` з новим паролем |
| AUTH-E2E-003 | Refresh token flow | `login` → `refreshToken` → `getProfile` зі старим access token (401) → `getProfile` з новим (200) |

## 10. Критерії готовності

### Definition of Done для тест-кейсу

- Тест написаний в `src/api/tests/` та використовує кастомний `test` із `api-fixture.ts`
- Тест не залишає даних у БД після виконання (DbCleaner або явний cleanup)
- Тест не залежить від порядку виконання інших тестів
- Happy path та мінімум 2–3 negative cases покриті для кожного ендпоінту
- Тест пройшов code review від Lead QA

### Definition of Done для модуля

- Всі тест-кейси з плану реалізовані та проходять локально
- Тести проходять у CI (`playwright.yml`)
- Немає `test.only` у коді

### Метрики покриття (ціль на кінець тижня 3)

|---|---|---|---|

## 11. Ongoing — покриття нових фіч

Після завершення основного блоку команда переходить у режим **ongoing**: нові ендпоінти покриваються паралельно з їх реалізацією в бекенді.

**Фічі в беклозі (не реалізовані, очікують тестування):**

| Фіча | Потенційні ендпоінти |
|---|---|
| Перекличка (roll call) в колі | `POST /api/groups/{id}/roll-call` або подібний |
| Повітряна тривога — підписка на регіон | Окремий модуль API |
| Push-сповіщення (FCM) — налаштування | Частково: `PUT /api/users/fcm-token` (є), логіка доставки — окремо |
| SMS-сповіщення | Зовнішній провайдер, інтеграційні тести |
| Агрегація статусів у колі | Може бути частиною GET /api/groups |
| Підтвердження видалення акаунту (модалка) | Логіка на рівні бекенду — DELETE /api/users |
| Геолокація | Окремий модуль |

**Правило для ongoing:**
1. Перед написанням тестів — узгодити Swagger або опис ендпоінту з бекенд-командою.
2. Написати тест-кейси (у вигляді коментарів або окремого md-файлу) до початку автоматизації.
3. Зробити code review перед merge.
